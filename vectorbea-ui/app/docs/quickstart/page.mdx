# Quickstart

This guide shows the fastest path to standing up the VectorBea Kotlin proxy in a customer-controlled environment. The goal is to put the proxy next to your AI agent or application service so prompt resolution stays local, while the proxy syncs published rules from the VectorBea cloud.

## Prerequisites

- Docker and Docker Compose available on the target machine or cluster node.
- A VectorBea API key or service credential that allows the proxy to sync published prompt rules.
- Network access from the proxy to the VectorBea control plane.
- A local application, service, or Python agent that can call the proxy over your chosen local interface.

## 1. Create an environment file

Create a `.env` file next to your Docker Compose definition:

```bash
VECTORBEA_API_URL=https://api.vectorbea.com
VECTORBEA_API_KEY=vb_live_xxxxx
VECTORBEA_WORKSPACE_ID=proj_123456789
VECTORBEA_PROXY_PORT=8090
```

Recommended variables:

- `VECTORBEA_API_URL` points to the control plane or hosted API.
- `VECTORBEA_API_KEY` authenticates the proxy when fetching published rules.
- `VECTORBEA_WORKSPACE_ID` scopes the proxy to the project/workspace it should serve.
- `VECTORBEA_PROXY_PORT` exposes the local listener your agents will call.

## 2. Run the proxy with Docker Compose

Use a minimal `docker-compose.yml` like this:

```yaml
services:
  vectorbea-proxy:
    image: vectorbea/proxy:latest
    restart: unless-stopped
    ports:
      - "${VECTORBEA_PROXY_PORT:-8090}:8090"
    env_file:
      - .env
```

Start the sidecar:

```bash
docker compose up -d
```

## 3. Verify the proxy is healthy

After startup, inspect the logs:

```bash
docker compose logs -f vectorbea-proxy
```

You should see the proxy:

- Starting its local listener.
- Authenticating against the VectorBea control plane.
- Pulling the latest published rules for the configured workspace or project.
- Refreshing its in-memory prompt cache.

## 4. Point your Python agent to the local proxy

Your application or agent should talk to the local proxy instead of embedding prompt text directly. A simple integration looks like:

```python
from vectorbea_client import VectorBeaProxyClient

client = VectorBeaProxyClient("http://127.0.0.1:8090")

prompt = client.resolve_prompt(
    prompt_name="summarize_ticket",
    variables={"ticket_text": ticket_text},
)
```

In production deployments, teams usually run the proxy:

- As a sidecar container in Kubernetes.
- On the same host as an internal job runner.
- As a colocated service inside a private VPC.

## 5. Publish prompt changes from the control plane

Once the proxy is running, prompt updates flow through the control plane:

1. Create or edit a prompt in VectorBea.
2. Publish the new version.
3. Let the proxy sync the updated prompt definition.
4. Keep your agent code unchanged while the governed prompt evolves.

## Operational tips

- Run one proxy instance per environment or per project boundary when you want clean blast-radius separation.
- Keep the API key scoped as narrowly as possible.
- Use project-level membership and publication workflows so development teams only affect their own prompts.
- Treat the proxy as infrastructure: monitor its startup logs, health endpoints, and sync status.
